# 변경 요청 센터 프로젝트

## 제품 목표

현업이 화면과 변경 내용을 지정해 1:1 문의를 접수하면, 개발자가 해당 화면에서 호출되는 소스와 수정 후보를 확인하고 현업에 답변한다. 분석 결과는 제안과 근거로 제공되며 변경의 적용은 개발자가 맡는다.

## 현재 상태

| 범위 | 상태 | 확인 내역 |
| --- | --- | --- |
| 로컬 MVP | 구현 및 API 검증 완료 | 보험 샘플의 계약 조회·보험료 계산·계약 변경 견적·사고 접수·보상 진행 조회, 문의 접수·담당·답변, Spring MCP 소스 추적, 파일 DB 저장 |
| 브라우저 검증 | 후속 후보 | HTML 응답과 스크립트 문법을 확인했다. 브라우저에서 역할별 전체 사용 흐름 확인이 남았다. |
| LLM 프로필 | 모의 서버 검증 완료 | Spring AI 호출에 문의와 MCP 근거가 포함되고 결과가 저장되는지 확인했다. 실제 모델을 통한 제안 품질은 후속 후보에 둔다. |

로컬 MVP는 샘플의 다섯 화면을 대상으로 하며, 화면별 호출 흐름은 에이전트의 MCP 도구에서 매핑한다. 샘플은 보험 업무만 실행하며, 에이전트는 빌드에 포함된 레거시 소스를 읽는다. H2 계정 로그인과 역할별 API를 사용한다. 현업의 문의와 첨부 접근 범위는 로그인 계정이 소유한 문의다. 운영 대상 계정 정책은 운영 전환 범위에서 결정한다.

## 첨부와 배포

문의에 스크린샷이나 참고 파일을 저장하고 역할별 문의 화면에서 확인한다. 이미지의 모델 분석은 `llm` 프로필을 사용한다. 두 앱의 실행 JAR와 런타임 SBOM은 Gradle 빌드로 만들고 CI에서 앱별 아티팩트로 보관한다. [실행과 산출물](README.md#배포-산출물과-sbom)

## 작업 기록

작업을 시작할 때 항목의 목표, 담당 역할, 수용 기준을 확인하고 상태를 `진행 중`으로 바꾼다. 구현 후 확인이 남으면 `검증 중`으로 표시한다. 수용 기준을 확인하면 `완료`로 표시하고 아래에 검증 결과를 기록한다. 제품 범위를 바꾸는 결정은 이유와 영향 범위를 함께 남긴다.

| 작업 | 결정 또는 검증 근거 |
| --- | --- |
| 로컬 MVP 기반 | 두 앱 빌드와 HTTP 검증으로 문의 흐름, 소스 줄 번호 일치, MCP 실패 후 재시도, 재시작 후 답변 보존을 확인했다. |
| 모델 선택 가능 | 기본 모드는 규칙으로 제안한다. 선택적 `llm` 프로필은 문의와 MCP 근거를 모델에 전달한다. |
| 첨부와 배포 산출물 | 기존 문의 호환, 파일 재조회와 재시작 보존, `file://` 제출, 모의 모델 이미지 입력, 실행 JAR의 런타임 의존성과 SBOM을 확인했다. |
| H2 계정 로그인 | 두 역할의 로그인과 반대 역할 API 차단, 로그인 세션과 CSRF, 다른 현업 계정의 문의·첨부 접근 차단, 계정 해시와 재시작 보존을 확인했다. |
| 레거시 화면 확장 | 다섯 화면의 등록과 MCP 근거 줄 번호를 대조했다. 계약 변경 견적, 30일 접수 경계, 접수 후 조회 및 상태별 검토일을 확인했다. |

실행과 데모 절차는 [README.md](README.md)에서 확인한다.
